# Codebase Concerns

**Analysis Date:** 2026-05-26

## Tech Debt

**Magic-link email transport is a no-op:** Issue: The `sendMagicLink` callback in `server/auth.ts` only logs the magic link URL to the console (`console.log()`). There is no email provider integration, so magic links are only usable in development where the console is visible. In production, users never receive their login email. Files: `server/auth.ts:22-24`, Impact: Production deployments cannot authenticate users — magic links are invisible. Fix approach: Integrate an email sending provider (Resend, SendGrid, SMTP) or add a note to `DEPLOY.md` that an SMTP-compatible transport must be wired in before going live.

**Hardcoded dev fallback for Better Auth secret and URL:** Issue: `server/auth.ts` uses `defaultSecret = "dev-only-better-auth-secret"` and `defaultBaseUrl = "http://localhost:3000"` when env vars `BETTER_AUTH_SECRET` / `BETTER_AUTH_URL` are missing. This means a production deployment that forgets these env vars will silently use a guessable signing secret and wrong base URL. Files: `server/auth.ts:12-14`, Impact: Session forgery, magic links pointing to localhost in production. Fix approach: Remove defaults and throw on missing `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` in non-development environments.

**No rate limiting on magic link sending:** Issue: The PRD (`tasks/prd-hermes-hub-mvp.md:300`) specifies "Apply rate limiting on magic link email sending (max 3 per 5 minutes per email)", but no rate limiting is implemented. Users can be spammed with magic links, and the endpoint is unprotected against brute-force enumeration of valid emails. Files: `server/app.ts:27-34`, `server/auth.ts`, Impact: Email spam, user enumeration. Fix approach: Add in-memory or DB-backed rate limiting on the `/api/auth/send-magic-link` endpoint.

**Duplicate migration files with skipped index:** Issue: The `drizzle/` directory contains three SQL migration files: `0000_overjoyed_titania.sql`, `0002_perfect_caretaker.sql`, and `0002_cuddly_xavin.sql`. There is no `0001_*` migration, and two files share the `0002` prefix. The `_journal.json` shows entries at idx 1 (tag `0002_perfect_caretaker`) and idx 2 (tag `0002_cuddly_xavin`), meaning migration ordering may not match the file name prefix convention. Files: `drizzle/0000_overjoyed_titania.sql`, `drizzle/0002_perfect_caretaker.sql`, `drizzle/0002_cuddly_xavin.sql`, `drizzle/meta/_journal.json`, Impact: Confusing migration history; potential for duplicate or skipped migrations when applying to a fresh database. Fix approach: Rename migrations to sequential `0001`, `0002` etc. and regenerate with `drizzle-kit`.

**Auth callback route overlaps verify route:** Issue: `server/app.ts` has both `GET /auth/verify-magic-link` and `GET /auth/callback` — both rewrite to `betterAuth.handler` at `/api/auth/magic-link/verify`. The callback endpoint is a duplicate that serves no distinct purpose. Files: `server/app.ts:37-55`, Impact: Unnecessary route duplication; any bug fix or change to verification flow must be done in both places (though currently they are identical). Fix approach: Remove `GET /auth/callback` and let the single verify endpoint handle both cases, or merge them with a shared handler.

## Known Bugs

**Telegram dashboard summary displays chat ID instead of bot username:** Symptoms: The dashboard Telegram summary card shows `@<numeric_chat_id>` as the bot username. The `toTelegramSummary()` function reads `telegramRecord.chatId` (a Telegram chat group ID, numeric) and renders it as `@${telegramRecord.chatId}` in the detail string. The actual bot username from `telegramConfigs` is stored in `botToken`/`chatId` but is only available during the `connectTelegram` response. Files: `server/dashboard.ts:178-186`, `server/telegram.ts`, Trigger: Connect a Telegram bot and view the dashboard. Workaround: The `chatId` field stores the bot's username at connect time (set as `bot.username` from `getMe`), so storing the actual username in `chatId` mitigates this. However, the field name is misleading and the detail string `@${chatId}` assumes a username, not a numeric ID.

**In-memory ephemeral credentials never expire:** Symptoms: Credentials stored via `storeEphemeralCredential()` in `server/credentials.ts` persist in a `Map` indefinitely — there is no eviction by age or session expiry. If a server restarts, all ephemeral credentials are lost. If a session remains open, the raw SSH password/key stays in memory forever. Files: `server/credentials.ts`, Trigger: Connect a server with `storeCredential: false` and leave the session open; the password or SSH private key remains in process memory. Workaround: None — this is a resource leak and security concern. Fix approach: Add a TTL-based eviction (e.g., clear entries older than 15 minutes) or tie cleanup to session expiry.

**SSE stream has no connection timeout:** Symptoms: `server/install.ts` uses `streamSSE()` from Hono, but the stream has no idle timeout. If a client opens the event stream and never closes it (e.g., lost network), the listener is never cleaned up unless the stream aborts. Files: `server/install.ts:162-199`, Trigger: Open an install stream and disconnect the client without closing EventSource. The listener remains registered, causing a potential memory leak if repeated. Fix approach: Add an idle timeout (e.g., 60 seconds of no data) that closes the SSE connection.

## Security Considerations

**Trusted `x-forwarded-for` header without validation:** Risk: All audit log entries and IP tracking use `context.req.header("x-forwarded-for")` directly with no validation or fallback chain. An attacker can spoof their IP in audit logs by sending a crafted `X-Forwarded-For` header, obscuring their true origin. Files: `server/servers.ts:49`, `server/server-actions.ts:134`, `server/install.ts:143`, `server/providers.ts:85`, `server/telegram.ts:86,135`, Impact: Audit log IP addresses are untrustworthy for forensics. Current mitigation: None — the header is used as-is. Fix approach: Use the direct remote address from the request socket (Hono `c.env.incoming` or `req.raw.socket.remoteAddress`) as the primary source, falling back to the last IP in `x-forwarded-for` chain only when behind a trusted proxy.

**BETTER_AUTH_SECRET hardcoded development fallback:** Risk: In any environment where `BETTER_AUTH_SECRET` is unset, the system falls back to `"dev-only-better-auth-secret"` — a publicly committed string. This allows anyone who reads the source code to forge session cookies. Files: `server/auth.ts:14`, Impact: Session hijacking in deployments that forget to set the env var. Current mitigation: The fallback is documented as dev-only, but there is no runtime guard. Fix approach: Throw on missing `BETTER_AUTH_SECRET` unless `NODE_ENV=development`.

**SSH private keys transmitted in plaintext JSON:** Risk: When connecting a server via SSH key, the entire private key content is sent as a JSON property in the POST body to `/api/servers/connect`. It is encrypted only at rest in the database. During transit, it relies on HTTPS (which is not enforced by the application). Files: `server/servers.ts:33-76`, `src/features/servers/connection-wizard.tsx`, Impact: If the production deployment uses plain HTTP (e.g., behind a misconfigured proxy), the private key is exposed in transit. Current mitigation: TLS is expected from the deployment environment. Fix approach: Add a server-side check that rejects non-HTTPS requests in production, and consider encrypting sensitive fields at the client side before transmission.

## Performance Bottlenecks

**Single database connection pool:** Problem: `server/db/index.ts` creates a `postgres` client with `max: 1`, meaning all concurrent requests share a single database connection. Any long-running query blocks all other database operations. Files: `server/db/index.ts:13-14`, Cause: The `max: 1` setting was likely chosen for simplicity during development. Impact: Dashboard load, install progress updates, and log fetching all queue up behind each other. Under concurrent user access, requests will experience increasing latency or timeout. Improvement: Increase `max` to a reasonable value (e.g., 10–20) based on expected concurrency, and consider using a connection pooler like PgBouncer for production.

**Multiple sequential DB queries in dashboard status:** Problem: `server/dashboard.ts` `getDashboardStatusSnapshot()` makes 5+ separate database queries (latest server, latest install, latest provider, latest telegram, server labels for action logs) — each as individual sequential `await` calls. Some of these could run in parallel. Files: `server/dashboard.ts:52-54`, `server/dashboard.ts:204-242`, Cause: Queries are fetched one after another with no `Promise.all`. Impact: Dashboard response time is the sum of all query latencies, not the max. Improvement: Use `Promise.all` for independent queries (install, provider, telegram configs can be fetched simultaneously).

**No caching for dashboard status polling:** Problem: The client polls `GET /api/dashboard/status` every 30 seconds. Each request triggers 5+ database queries and an SSH connection to the VPS for live metrics — all without caching or ETag support. Files: `src/features/dashboard/status-overview.tsx:65`, `server/dashboard.ts`, Cause: No caching layer or conditional requests (no `If-None-Match` / `Last-Modified` headers). Impact: Unnecessary load on the database and SSH infrastructure for every client polling interval. Improvement: Add HTTP caching headers (`Cache-Control: max-age=10`) or use a short-lived in-memory cache for the dashboard snapshot.

## Fragile Areas

**Install workflow — `server/install.ts` (623 lines):** Files: `server/install.ts`, Why fragile: This single file handles the entire install orchestration: HTTP request handling, SSH execution, SSE event streaming, database persistence, audit logging, and install state management. The install steps are hardcoded as a constant array with embedded shell commands. Any change to install flow (adding/removing steps, error handling, rollback logic) requires modifying this large, tightly coupled file. Safe modification: Extract the install steps into a configurable pipeline (e.g., a list of `{id, command, progress}` records that can be individually tested). Split the `runInstallWorkflow` into discrete phases: SSH connection, step execution, event emission, and DB persistence. Test coverage: The test file (`server/install.test.ts`) tests the happy path, ephemeral credential failure, and SSE replay, but does not test: SSH connection failures at each step, partial step failures, concurrent install race conditions, or SSE timeout/reconnect behavior.

**In-memory credential store — `server/credentials.ts`:** Files: `server/credentials.ts`, Why fragile: Ephemeral credentials are stored in a plain `Map` with no size limit, TTL, or cleanup mechanism. If a user connects many servers without storing credentials, each raw SSH password/key remains in memory until the process restarts. A memory leak or credential exposure is possible. Safe modification: Add a `setInterval` cleanup that removes entries older than 15 minutes. Consider using `WeakRef` or a capped `Map` with LRU eviction. Track ephemeral credential count with a metric. Test coverage: No tests exist for `server/credentials.ts` — both `storeEphemeralCredential` and `getEphemeralCredential` are untested.

**OS validation — `server/ssh.ts`:** Files: `server/ssh.ts:62-120`, Why fragile: The `parseAndValidateOs` function only accepts Ubuntu 22.04+ and Debian 12+. It rejects all other Linux distributions (RHEL, Fedora, CentOS, Arch, Alpine) outright. As Hermes is a Docker-based deployment, it could technically run on any Linux distribution with Docker support, but the validation gate blocks non-Ubuntu/Debian VPS connections entirely. Safe modification: Add support for additional distributions (at minimum RHEL 8+, Fedora, and generic Docker-capable Linux). Better yet, change the validation to warn about untested OSes rather than rejecting them, since Docker itself is distribution-agnostic. Test coverage: Only two tests exist — Ubuntu 22.04 (pass) and Ubuntu 20.04 (reject). No tests for Debian 12, Debian 11, RHEL, or edge cases like missing `/etc/os-release`.

**Auth base URL construction — `src/lib/auth-client.ts`:** Files: `src/lib/auth-client.ts`, Why fragile: During SSR (server-side rendering), the `baseURL` defaults to `"http://localhost:3000/api/auth"` because `typeof window === "undefined"`. This means magic link verification URLs generated during SSR point to `localhost:3000` instead of the actual production domain. Safe modification: Use the request's origin or the configured `BETTER_AUTH_URL` env var for the SSR base URL. Test coverage: No tests for the `auth-client.ts` module or the SSR base URL behavior.

## Dependencies at Risk

**`better-auth` (^1.6.11):** Risk: This is a relatively new auth library (v1.x) with an evolving API. Breaking changes in minor releases are possible. The project uses both `@better-auth/drizzle-adapter` and the `tanstackStartCookies()` plugin, which may have compatibility issues. Impact: An update could break the magic-link auth flow, session handling, or cookie management. The hardcoded dev fallback for `BETTER_AUTH_SECRET` compounds the risk.

**`node-ssh` (^13.2.1):** Risk: SSH library that wraps `ssh2`. Version 13.x may have compatibility issues with newer SSH server configurations or key formats (e.g., ED25519 keys, FIDO/U2F keys). Key-based auth flow assumes the private key content is passed as a string. Impact: Users with non-standard SSH configurations may be unable to connect their VPS. There is no fallback to the `ssh2` library directly if `node-ssh` hits a limitation.

**All TanStack libraries at `"latest"`:** Risk: The `package.json` specifies `"latest"` for `@tanstack/react-router`, `@tanstack/react-start`, `@tanstack/react-router-devtools`, and others, rather than pinned versions. This means `bun install` or `bun update` could pull in breaking changes without warning. Impact: Build failures or runtime behavioral changes could occur after routine dependency installs. The project's auto-generated `routeTree.gen.ts` is particularly sensitive to router API changes.
