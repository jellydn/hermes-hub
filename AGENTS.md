# HermesHub

## Commands

- Use `bun`, not `npm` or `pnpm`. The lockfile is `bun.lock`.
- Main local commands are `bun run dev` (Vite on port `3000`), `bun run build`, `bun run test`, `bun run test:coverage`, `bun run typecheck`.
- `bun run test:coverage` runs tests with coverage report and threshold check. `bun run db:generate` writes a new Drizzle migration from the current schema; `bun run db:migrate` runs `scripts/db-migrate.mjs` (a thin `DATABASE_URL` guard around `drizzle-kit migrate`); `bun run preview` serves the built bundle; `bun run brand:assets` regenerates brand assets.
- `just dev`, `just test`, `just typecheck`, `just ci`, `just check`, `just lint`, `just format`, `just install`, `just db-generate`, `just db-migrate` are thin wrappers around the Bun scripts. `just ci` is the full lint → typecheck → test → build pipeline. `just check` runs typecheck + test in parallel (limited to 6 vitest workers, overridable via `VITEST_MAX_WORKERS`).
- CI (`.github/workflows/ci.yml`) runs `bunx @biomejs/biome check .`, then `bun run typecheck`, then `bun run test:coverage` (with artifact upload), then `bun run build`. Match that order when you touch JS/TS files. The deploy workflow also runs the same gate before shipping.
- Do not use `bun test`; Vitest is configured in `vite.config.ts` and the repo's test command is `bun run test` (uses `--passWithNoTests --reporter=dot`).
- Pre-commit (`.pre-commit-config.yaml`) runs biome-check, then `bun run typecheck`, then `react-doctor --staged --blocking warning` on staged changes.
- Production start is `node scripts/start-production.mjs` (not Bun) — invoked by the Dockerfile `CMD` and by Dokku. It runs `drizzle-kit migrate` first when `DATABASE_URL` is set, then serves `dist/client/` static assets and the SSR bundle from `dist/server/server.js` on `HOST`/`PORT` (defaults `0.0.0.0:3000`).
- Local dev infra lives in `compose.yaml`: Postgres 17 + mailpit (SMTP on `:1025`, web UI on `:8025`) for catching magic-link emails. `bun run dev` itself runs Vite only — start the stack separately with `docker compose up -d postgres mailpit` (or `docker compose up -d postgres` if you don't need mail).

## Verified Gotchas

- `vite.config.ts` excludes `node-ssh`, `ssh2`, and `cpu-features` from `optimizeDeps` because server-only SSH code pulls native `.node` binaries that break Vite dev prebundling if reintroduced into the client scan. Do not add server-only native deps to the client include list.
- `src/routeTree.gen.ts` is generated by the TanStack Router plugin. Do not edit it by hand. `biome.json` excludes it from lint/format via the `files.includes` negation.
- `biome.json` also has a per-file override for `src/lib/use-mount-effect.ts` that disables `useExhaustiveDependencies` — this is the deliberate mount-only escape hatch. Keep that override in place if you add more files in that pattern.
- Path aliases (kept in sync between `tsconfig.json` `paths` and `package.json` `imports`; Vite uses `resolve.tsconfigPaths: true`):
  - `#/*` → `./src/*`
  - `#server/*` → `./server/*`
  - `#shared/*` → `./shared/*`
  - The earlier `@/*` alias was consolidated into `#/*` in ADR 0012 — do not reintroduce it.
  - `server/` and `shared/` modules never use the `#` aliases internally (they use `../`); the aliases are only for cross-directory imports from `src/`.
- `tsc` is strict: `noUnusedLocals`, `noUnusedParameters`, `verbatimModuleSyntax: true`. Use `import type` for type-only imports — Biome and the build will flag plain `import` of a type-only symbol.
- Vitest is configured with `environment: "node"` in `vite.config.ts` and globs `src/**` and `server/**` for `*.{test,spec}.{js,ts,jsx,tsx}` files. Use `node:test`-style globals or import from `vitest`; do not assume a DOM. The repo convention is `*.test.{ts,tsx}` (the `__snapshots__/` and `__tests__/` directories under `server/` are not test files — they hold fixtures and snapshot outputs that test files reference).
- There are no tests under `src/routes/` or `src/features/` yet — follow the `src/lib/` pattern if you add any.
- `drizzle.config.ts` reads `DATABASE_URL` from env (falls back to `""` — no crash on import). The actual gates are: `scripts/db-migrate.mjs` exits 1 if `DATABASE_URL` is unset, `scripts/start-production.mjs` skips migration with a warning if it's unset, and `server/db/index.ts` `getDb()` throws "DATABASE_URL is required" on first call.
- Required env vars: `DATABASE_URL`, `ENCRYPTION_KEY` (generate with `openssl rand -hex 32`), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`. See `.env.example`. The `ENCRYPTION_KEY` is hex-decoded to 32 bytes; rotating it invalidates all stored SSH credentials.
- `server/auth.ts` is intentionally lazy (`getAuth()` builds the Better Auth instance on first call, `getAuthSession()` short-circuits to `null` when `DATABASE_URL` is missing). Do not hoist auth init to module scope — pages will crash on first render if env vars are unset.
- `src/lib/auth-client.ts` uses an absolute SSR base URL from `BETTER_AUTH_URL` (fallback `http://localhost:3000/api/auth`). Keep it absolute.
- Mutating API routes in `server/app.ts` are wrapped in `httpsMiddleware` → `requireHttps()`. In production, the guard requires either `https://` on the request URL or `x-forwarded-proto: https` from the upstream proxy. The check uses `globalThis.process.env.NODE_ENV` (not `process.env.NODE_ENV`) to avoid Vite's build-time constant replacement tree-shaking the dev-only early return. Add `httpsMiddleware` to any new credential-bearing mutating route. The guard also applies to credential-adjacent reads (`/servers/:id/install/events`, `/servers/:id/install/log`, `/servers/:id/web-ui`) because their error paths can echo credential material (host keys, install logs, compose env).
- The deploy pipeline (`.github/workflows/deploy.yml`) ships to two targets:
  - `vps` — Docker Compose on a VPS; image is built and pushed to GHCR by the workflow, then `docker compose pull app` + `drizzle-kit migrate` + `docker compose up -d`. Only runs when `vars.DEPLOY_TARGET` is `vps`.
  - `dokku` — `git push --force dokku HEAD:main` after `config:set` on the app. The app's Dokku deploy branch is `main`. Force is required because that git repo often diverges from GitHub after manual deploys. The job uses the `production` GitHub Environment and a pinned `DOKKU_SSH_KNOWN_HOSTS` secret instead of `ssh-keyscan`. Runs on every push to `main` unless `vars.DEPLOY_TARGET` is explicitly `vps`, and also on manual dispatch with `target: dokku`. The job fails the deploy when the app has no TLS certificate (checked via `dokku letsencrypt:active` / `dokku certs:report`), except on the very first deploy of a newly created app — without TLS, `NODE_ENV=production` + `httpsMiddleware` returns 426 for credential-bearing routes. The Dokku SSH port defaults to 22; set the `DOKKU_SSH_PORT` secret to override it (mirrors the VPS path's `VPS_PORT`). Optional dispatch input `correlation` is used by `scripts/setup-dokku-deploy-secrets.sh --rerun` to watch the run it started.
  - Manual dispatch accepts a `target` input (`vps` or `dokku`) that overrides the repo var for one run.
  - On push to `main`, the dokku job runs by default (unless `DEPLOY_TARGET=vps`), and the VPS job runs only when `DEPLOY_TARGET=vps`. Required Dokku secrets: `DOKKU_HOST`, `DOKKU_SSH_PRIVATE_KEY`, `DOKKU_APP`, `DOKKU_SSH_KNOWN_HOSTS`, `DATABASE_URL`, `ENCRYPTION_KEY`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`. Optional: `DOKKU_SSH_PORT`, `RESEND_API_KEY`, `RESEND_FROM`. Configure required reviewers on the `production` GitHub Environment if unattended deploys should wait for approval.
- Single-instance boundary (per `docs/adr/0009-single-instance-boundary-for-operational-state.md`): install SSE streams, session credentials (`server/credentials.ts`), the magic-link rate limiter (`server/app.ts` `magicLinkRateLimiter`), and the dashboard caches (`server/dashboard/metrics.ts`) are in-memory module-level state. They are not shared across nodes and are accepted as a temporary constraint. Do not put anything that must be shared behind them.
- A separate React Doctor workflow (`.github/workflows/react-doctor.yml`) scans the codebase on every PR and on push to `main`, posting a sticky health-score comment. It's read-only; failures are advisory unless `fail-on: warning` is enabled in the workflow.

## Architecture

- `src/server.ts` is the unified server entrypoint. It sends `/api/*` requests to the Hono `apiApp` exported from `server/app.ts` and everything else to TanStack Start. Production `scripts/start-production.mjs` imports the built bundle from `dist/server/server.js`.
- `server/app.ts` mounts every Hono route (`/api/servers`, `/api/dashboard/status`, `/api/logs`, `/api/providers/*`, `/api/settings/*`, `/api/telegram/*`, `/api/auth/*`, `/api/health`, etc.). When adding a new endpoint, register it here.
- `server/` holds the real backend logic: auth (`auth.ts`), DB (`db/`), SSH (`ssh/`), install orchestration (`install/`), dashboard aggregation (`dashboard/`), providers (`providers/`), Telegram (`telegram/`), server records and actions (`servers.ts`, `server-actions.ts`, `server-detail-snapshot.ts`, `server-records.ts`), settings (`settings/`), Hermes runtime (`hermes/`), web UI proxy (`web-ui/`), shared helpers (`lib/`), crypto/credentials.
- `shared/contracts/` holds cross-boundary types (e.g. `ServerActionType`, `ServerDetailSnapshot`) safe to import from both `src/` and `server/`.
- `src/routes/` contains file-based TanStack Start routes. Keep route files thin — push UI into `src/features/`. Authenticated dashboard pages reuse `AppShell` from `src/routes/dashboard.tsx`.
- `src/features/<domain>/` — one folder per product area (`servers`, `telegram`, `settings`, `providers`, `dashboard`, `logs`, `auth`, `landing`, `about`). Page-specific hooks and components live here.

## Data Flow Conventions

- Route-level `createServerFn` loaders are the normal pattern for authenticated page snapshots such as dashboard, logs, AI provider, settings, and Telegram.
- `src/routes/servers.$id.tsx` is the exception: it fetches `/api/servers/:id` from the component with `useMountEffect` instead of using a route loader. Follow the existing pattern unless you are intentionally reshaping that page.
- Install progress lives in two places: persisted `install_events` rows (the single source of truth) and the in-memory SSE stream in `server/install/sse-stream.ts`. When you change install events or replay behavior, keep both the rows and the in-memory stream in sync. `server/install/workflow.ts` orchestrates the remote install, and `server/install/records.ts` is the persistence layer.
- Server action history is read from `audit_logs` rows named `server.action.*.succeeded|failed`, filtered by the indexed `audit_logs.server_id` column (not by JSON `details.serverId`) before `LIMIT 5`. The list query in `server/servers/list.ts` keys records on the returned `serverId` column.
- Rollback target resolution is `request targetVersion → audit history imageRef → installs.version → "latest"`. The implementation lives in `server/server-detail-snapshot.ts` (`resolveRollbackTarget`, `resolveRollbackTargetFromSources`, `getRollbackTargetFromHistory`) and is called from `server/server-actions.ts` for the `rollback` action.

## Auth And Runtime Constraints

- Better Auth is intentionally lazy in `server/auth.ts` (`getAuth()` builds the instance on first call, `getAuthSession()` returns `null` when `DATABASE_URL` is missing). Do not hoist auth initialization to module scope.
- The magic-link rate limiter is keyed by `email`, not IP (`magicLinkRateLimiter` in `server/app.ts`, 3 requests / 5 min, 5 min block). It is in-memory, so a second instance would not share the budget.
- `apiApp.post("/auth/send-magic-link", …)` rewrites the path to `/api/auth/sign-in/magic-link` and proxies to `getAuth().handler(...)`. The catch-all `apiApp.on(["GET", "POST"], "/auth/*", …)` also applies the rate limit to direct hits on `/api/auth/sign-in/magic-link`. Keep both branches in sync if you change the limiter.
- Mutating API routes in `server/app.ts` call `requireHttps()` in production. Preserve that guard on new credential-bearing endpoints. The dev shortcut is intentional; do not remove the `globalThis.process` indirection.

## Frontend Conventions

- Prefer the shared `cn()` helper (`src/lib/utils.ts`) and existing UI primitives in `src/components/ui/`.
- Keep helper text and validation text outside `<label>` elements so Testing Library queries and browser automation keep stable accessible names.
- The repo has a deliberate mount-only escape hatch in `src/lib/use-mount-effect.ts`; use it for stable external subscriptions like polling or SSE when that pattern already exists. Biome's `useExhaustiveDependencies` rule is disabled for that file — do not enable it.
- For "read the latest reducer state inside an async handler" (e.g. trust-and-retry flows that started on an older commit), import `useStaleRef` from `src/lib/use-stale-ref.ts` instead of rolling a local `useRef(state); ref.current = state;` pair — that pattern is easy to get wrong and is now the established helper.
- Forms use `react-hook-form` + `zod` (via `@hookform/resolvers`) per ADR 0008. Resolvers and validators live alongside the form in `src/features/<domain>/`.

## Database Conventions

- Drizzle schema lives in `server/db/schema.ts`. Re-exported Better Auth tables (`user`, `session`, `account`, `verification`) sit at the bottom of that file.
- App-owned primary keys generally use `text(...).primaryKey().default(sql\`gen_random_uuid()::text\`)`. Follow that pattern for new app tables unless an external integration forces a different key shape.
- Table names: snake_case plural (`servers`, `install_events`, `audit_logs`, `mcp_servers`, `agent_skills`).
- After changing the schema, `bun run db:generate` to write a new SQL file into `drizzle/` and `bun run db:migrate` to apply locally. The deployment pipeline runs migrations automatically (see `scripts/start-production.mjs` and the VPS deploy step that runs `drizzle-kit migrate` after pulling the image).

## DB Transaction Boundaries

Use `db.transaction()` when a write path touches multiple Drizzle statements that must commit or roll back together to maintain consistency. The current transaction boundaries are:

- **`server/telegram.ts` — `deployTelegramToServer`:** SSH deploy succeeds, then config update + success audit log insert are wrapped in a single transaction. If the transaction fails, deploy state (`deployedServerId`, `deployedServerHost`, `apiServerKey`) is not persisted, keeping local DB consistent with the remote Hermes container.
- **`server/server-actions.ts` — `runServerAction`:** SSH action succeeds, then success audit log + install version update (SELECT then UPDATE on `installs`) are wrapped in a single transaction. If the version update fails, the audit log also rolls back, so rollout history and install version stay in sync.
- **`server/install/sse-stream.ts` — `emitInstallEvent`:** `install_events` row insert + `installs` row update are wrapped in a single transaction. If the update fails, the event row rolls back too, so SSE replay and the persisted install row never disagree.

**When to use transactions:** When a secondary write (e.g., audit log) is coupled to a primary write (e.g., config update), and the primary write being committed without the secondary would cause an inconsistent or unrecoverable state. Examples: deploy state changes, version tracking updates.

**When sequential writes are fine:** Primary data → audit log sequences where the audit log is purely historical and its absence doesn't affect correctness (e.g., server connect/disconnect, provider save, `server.install.started`). If the audit insert fails, the primary operation is still valid — no data divergence.

## Cursor Cloud specific instructions

- The startup update script only runs `bun install`. Bun and a local PostgreSQL server are provisioned into the VM image (not by the update script), and no services are auto-started.
- Local Postgres is a native `apt` install (not Docker — Docker is not available here). Start it with `sudo pg_ctlcluster 16 main start` before running the app or migrations. The dev role/DB are `hermes` / `hermes` / `hermes_hub` (`DATABASE_URL=postgresql://hermes:hermes@localhost:5432/hermes_hub`). Docker Compose (`compose.yaml`) is not usable here; use the native Postgres instead of `docker compose up -d postgres`.
- `.env` is required and gitignored. It must define `DATABASE_URL`, `ENCRYPTION_KEY` (`openssl rand -hex 32`), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=http://localhost:3000`. Create it from `.env.example` if missing.
- `.env` is NOT auto-loaded by `bun run <script>` for child `node` processes (e.g. `bun run db:migrate` spawns `node scripts/db-migrate.mjs` and sees no `DATABASE_URL`). Export the env first in the shell: `set -a; . ./.env; set +a`. `bun run dev` (Vite) works either way, but exporting `.env` into the shell is the reliable pattern for every command.
- Migration-from-scratch is broken: `drizzle/0009_same_jackal.sql` runs `DROP INDEX "server_web_ui_server_id_idx"`, but no `.sql` migration ever creates that index (it only exists in `drizzle/meta/*_snapshot.json`), so `bun run db:migrate` fails on a fresh DB and (via the single-transaction postgres-js migrator) rolls the whole chain back — leaving zero tables. To materialize the schema locally, run `bunx drizzle-kit push` (with `.env` exported) instead; it syncs `server/db/schema.ts` directly. CI never runs migrations from scratch, which is why this is not caught upstream.
- In dev (`NODE_ENV` != production) with `RESEND_API_KEY` unset, magic-link login URLs are logged to stdout by `server/lib/send-magic-link-email.ts` — grab the link from the dev server output to complete login without any email server. Mailpit/Resend are not needed for local login.
- `bun run dev` serves both the frontend and the Hono `/api/*` on port 3000. Health check: `curl http://localhost:3000/api/health` returns `{"status":"ok","database":"connected"}` once Postgres is up and the schema is present.
